# Planify — Roadmap de construcción del MVP

**Basado en:** `PLANIFY.md` (consolidación del 2026-10-11)
**Recorrido central a validar:** `Idea → Objetivos → Requisitos → Historias → Tareas → Revisión`

---

## 1. Visión

- **Qué es:** una aplicación web colaborativa que convierte una idea en una planificación de software organizada, revisable y **trazable manualmente** antes de empezar a desarrollar.
- **Para quién:** equipos de estudiantes que desarrollan proyectos académicos de software (sin depender de docentes, cursos ni grupos).
- **Problema:** los equipos pierden la relación entre lo que quieren construir (objetivos, requisitos) y el trabajo necesario para implementarlo (historias, tareas).
- **Diferenciador:** trazabilidad manual + comprobaciones estructurales + aprobación final del propietario.
- **Restricciones:** monolito modular en TypeScript, sin IA, sin API pública, sin microservicios; integridad garantizada por PostgreSQL, no solo por el backend.

---

## 2. Stack tecnológico

| Capa | Elección | Por qué |
|---|---|---|
| Runtime | Node.js 24 LTS | Definido en el documento |
| Framework | Next.js 16.x (App Router) + React 19 + TypeScript 7 | Frontend y backend en una sola app |
| Estilos / UI | Tailwind CSS 4 + shadcn/ui | Componentes accesibles y rápidos de adaptar |
| Validación | Zod | Misma validación en Server Actions y servicios |
| Base de datos | PostgreSQL administrado por Supabase | Claves foráneas compuestas e índices parciales nativos |
| ORM / migraciones | Drizzle ORM + Drizzle Kit | Restricciones SQL explícitas y migraciones revisables |
| Autenticación | Better Auth (correo y contraseña) | Fuente de verdad de identidad; **no** se usa Supabase Auth |
| Pruebas | Vitest (unitarias/integración) + Playwright (`pnpm exec playwright`) | Integridad de BD y flujos de navegador |
| Paquetes | pnpm | Definido en el documento |
| Despliegue | **Diferido hasta terminar el MVP** (Vercel para la app + Supabase para la BD) | Durante el desarrollo todo corre en local contra Supabase remoto |

**Decisiones técnicas que condicionan todo el plan**

1. Los IDs de usuario son `TEXT` (Better Auth). Toda FK de identidad usa `text`, nunca `BIGINT`.
2. Las tablas de dominio usan `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
3. Las operaciones críticas (aceptar invitación, transferir propiedad, aprobar, purgar) son **servicios de servidor transaccionales**, nunca lógica dentro de componentes.
4. Drizzle solo se importa en el servidor; las credenciales de Supabase nunca llegan al navegador.
5. **No se despliega durante el desarrollo.** La app corre en local y se conecta a Supabase con la conexión directa. El despliegue se hace en la Fase 8, al terminar el MVP; allí se evaluará el *pooler* en modo transacción con *prepared statements* desactivadas, porque Vercel es serverless.

## 3. Modelo de datos completo (diseñado desde el inicio)

Se define todo el esquema ahora para evitar rediseños; cada tabla se **crea en la fase indicada**.

### Identidad (generado por Better Auth)
`user`, `session`, `account`, `verification` → se generan con el CLI de Better Auth y se conservan como fuente oficial (`src/db/auth-schema.ts`).

### Dominio

| Tabla | Propósito | Fase |
|---|---|---|
| `projects` | Proyecto, datos de definición, estado, aprobación, ciclo de eliminación | 1 |
| `project_members` | Membresía y rol (`owner`/`editor`/`reader`) | 1 |
| `project_sections` | Secciones de la plantilla (habilitadas/omitidas/obligatorias) | 1 |
| `planning_items` | Tabla común de objetivos, requisitos, historias y tareas | 2 |
| `requirement_details` | `requirement_kind`, `priority` | 2 |
| `user_story_details` | `user_role`, `user_need`, `user_benefit`, `requires_implementation` | 2 |
| `story_acceptance_criteria` | Criterios independientes y ordenados por historia | 2 |
| `task_details` | `task_kind`, `work_status`, `priority`, `position` | 2 |
| `traceability_links` | Relaciones con FK compuestas `(project_id, item_id)` | 3 |
| `project_invitations` | Enlaces con `token_hash`, usos y vigencia | 5 |
| `project_invitation_acceptances` | Registro de cada aceptación | 5 |
| `ownership_transfer_requests` | Solicitud → aprobación de transferencia | 5 |
| `item_comments` *(opcional)* | Comentarios en requisitos, historias y tareas | 7 |

### Relaciones clave

- `projects.owner_id` → `user.id` (**fuente canónica** del propietario; `project_members` con rol `owner` es derivado y se sincroniza en la misma transacción).
- `planning_items.project_id` → `projects.id`, con índice único `(project_id, id)` para habilitar FK compuestas.
- `traceability_links` referencia `(project_id, source_item_id)` y `(project_id, target_item_id)` hacia `planning_items(project_id, id)`.
- Las tablas de detalle usan `item_id` como PK y FK hacia `planning_items`.

## Fase 3 — Trazabilidad manual y matriz
*Meta: conectar los elementos y ver qué está conectado y qué falta.*
*Depende de: Fase 2 · Esfuerzo: 2-3 sesiones*

### Qué hay de nuevo
- Botón `Relacionar` con búsqueda y selección del destino, iniciable desde cualquier extremo.
- Relaciones entrantes y salientes visibles en cada elemento.
- Matriz de trazabilidad básica en tres tramos.

### Base de datos
- `traceability_links` con claves foráneas compuestas e índice de unicidad.

```sql
ALTER TABLE traceability_links
  ADD CONSTRAINT tl_source_fk
    FOREIGN KEY (project_id, source_item_id)
    REFERENCES planning_items (project_id, id),
  ADD CONSTRAINT tl_target_fk
    FOREIGN KEY (project_id, target_item_id)
    REFERENCES planning_items (project_id, id),
  ADD CONSTRAINT tl_unique
    UNIQUE (project_id, source_item_id, target_item_id);
```

**Qué hace este bloque:**
- `tl_source_fk` y `tl_target_fk` obligan a que ambos extremos existan **y** pertenezcan al mismo proyecto que el vínculo; así una relación nunca cruza proyectos.
- `tl_unique` impide relaciones duplicadas entre los mismos elementos.

### Reglas de dominio (en el servicio, no en la BD)
- Cadena principal: `Objetivo → Requisito → Historia → Tarea` (`link_kind = primary`).
- Un elemento no puede relacionarse consigo mismo.
- Relaciones secundarias: se normaliza el orden de los extremos antes de guardar para evitar duplicados invertidos.
- Las tareas técnicas no necesitan historia.
- El servicio valida las combinaciones de tipos permitidas y decide si el vínculo es principal o secundario.

### Checklist

#### Datos
- [ ] Esquema Drizzle de `traceability_links` con las dos FK compuestas y `UNIQUE`.
- [ ] Índices por proyecto, origen y destino.

#### Servidor
- [ ] `TraceabilityService.createLink` / `deleteLink` con validación de tipos permitidos.
- [ ] Consultas de relaciones entrantes y salientes por elemento.
- [ ] Marcar en las consultas los vínculos que apuntan a elementos archivados.

#### Frontend
- [ ] Diálogo `Relacionar` con búsqueda (objetivo: ≤ 4 acciones desde abrir el elemento origen).
- [ ] Panel de relaciones entrantes/salientes en cada elemento.
- [ ] Matriz en tres tramos: Objetivos↔Requisitos, Requisitos↔Historias, Historias↔Tareas, con celdas faltantes resaltadas.
- [ ] Aviso visual cuando un vínculo apunta a un elemento archivado.

#### Pruebas
- [ ] Una relación con `source_item_id` de otro proyecto es rechazada.
- [ ] Una relación con `target_item_id` de otro proyecto es rechazada.
- [ ] Una relación hacia un elemento inexistente es rechazada.
- [ ] No se permiten duplicados ni autorrelaciones.
- [ ] Archivar un elemento conserva sus relaciones.
- [ ] E2E: crear una relación en ≤ 60 s y ≤ 4 acciones.

### Definición de terminada
- Desde cualquier elemento se consulta su origen y sus conexiones.
- La matriz refleja con exactitud los vínculos existentes y faltantes.

## Fase 4 — Comprobaciones, cobertura y aprobación
*Meta: saber si el proyecto está listo y que el propietario pueda aprobarlo.*
*Depende de: Fase 3 · Esfuerzo: 2-3 sesiones*

### Qué hay de nuevo
- Cálculo de cobertura estructural por control.
- Lista de comprobaciones bloqueantes y no bloqueantes.
- Estados `borrador → en revisión → preparado`, con aprobación registrada.
- Reapertura automática ante cambios relevantes.

### Reglas clave
- **Cobertura** = obligaciones satisfechas / obligaciones aplicables × 100. Sin obligaciones aplicables → `No aplica` (**nunca** 100 %).
- **Contenido mínimo** (independiente de la cobertura): un objetivo, un requisito y una historia activos; criterios de aceptación completos cuando correspondan; tareas para historias que requieran implementación; relaciones obligatorias de la cadena principal.
- Un proyecto vacío **no** se puede aprobar aunque todo aparezca como `No aplica`.
- Los elementos archivados no cuentan como activos.

| Situación | Resultado |
|---|---|
| Contenido mínimo faltante | Bloquea |
| Relación obligatoria faltante | Bloquea |
| Elemento opcional incompleto | No bloquea |
| Tarea técnica sin historia | No bloquea |
| Relación secundaria faltante | No bloquea |

### Checklist

#### Servidor
- [ ] `TraceabilityCoverageService`: cobertura por control (objetivos→requisitos, requisitos→historias, historias→tareas, criterios completos).
- [ ] `ReadinessChecksService`: devuelve lista de incumplimientos con tipo (bloqueante / no bloqueante).
- [ ] `ApproveProjectReadinessService`: exige contenido mínimo + criterios completos + 0 bloqueantes + confirmación del propietario; guarda `approved_by` y `approved_at`.
- [ ] Reapertura a `in_review` según la tabla del documento (cambios en descripción/alcance/objetivo, requisitos, historias, tareas sustanciales, relaciones relevantes, archivado de elementos necesarios).
- [ ] No reabrir por: prioridad/orden/estado de tareas, comentarios, perfil, cambios de integrantes no críticos.

#### Frontend
- [ ] Pantalla `Revisión` con checks, cobertura por control y botón de aprobar (solo propietario).
- [ ] Indicador de estado del proyecto en el encabezado.
- [ ] Mensaje explícito que separa **cobertura estructural** de **precisión funcional**.

#### Pruebas
- [ ] Un proyecto vacío no se puede aprobar.
- [ ] Las comprobaciones ignoran elementos archivados.
- [ ] Una tarea técnica independiente no cuenta como vínculo faltante.
- [ ] La aprobación registra quién y cuándo.
- [ ] Un cambio de reapertura devuelve `ready` a `in_review`; un cambio de estado de tarea no.
- [ ] Las transacciones críticas se revierten completas ante un error.

### Definición de terminada
- **Hito de uso individual:** una persona puede planificar y aprobar un proyecto de punta a punta.

## Fase 5 — Colaboración: invitaciones, roles y transferencia
*Meta: un equipo completo trabaja en el mismo proyecto de forma segura.*
*Depende de: Fase 4 · Esfuerzo: 3-4 sesiones*

### Qué hay de nuevo
- Enlaces de invitación controlados (`activo`, `revocado`, `expirado`, `agotado`).
- Aceptación **atómica** (un enlace no concede acceso por sí solo).
- Administración de integrantes y roles.
- Transferencia de propiedad mediante solicitud y aprobación.

### Base de datos
- `project_invitations` (solo `token_hash`, `max_uses`, `uses_count`, `expires_at`).
- `project_invitation_acceptances` con `UNIQUE(invitation_id, user_id)`.
- `ownership_transfer_requests` con índice único parcial (una pendiente por proyecto).

### Flujo de aceptación

```text
Abrir enlace → Autenticarse o registrarse → Aceptar → Validar vigencia → Crear membresía
```

```ts
// Esquema conceptual de AcceptProjectInvitationService
await db.transaction(async (tx) => {
  const inv = await lockInvitation(tx, tokenHash);      // SELECT ... FOR UPDATE
  assertActive(inv);                                    // estado, expiración, usos
  await assertNotMember(tx, inv.projectId, userId);     // sin membresía previa
  await createMembership(tx, inv, userId);              // rol asignado
  await recordAcceptance(tx, inv, userId);              // registro de aceptación
  await incrementUses(tx, inv);                         // uses_count + 1
  await markExhaustedIfNeeded(tx, inv);                 // estado agotado
});
```

**Qué hace cada línea:**
- `lockInvitation` bloquea la fila: si hay un solo uso disponible, solo una solicitud simultánea puede consumirlo.
- `assertActive` vuelve a verificar la vigencia en el backend (aunque el enlace fuera válido al abrirse).
- `assertNotMember` + `createMembership` evitan duplicar membresías (respaldado por `UNIQUE(project_id, user_id)`).
- `recordAcceptance` deja el rastro: invitación, usuario, proyecto, rol y fecha.
- `incrementUses` y `markExhaustedIfNeeded` mantienen el contador coherente y cierran el enlace al agotarse.
- Todo ocurre en una sola transacción: si algo falla, no queda nada a medias.

### Flujo de transferencia de propiedad
1. Un editor crea la solicitud (`pending`, vigencia 14 días).
2. El propietario aprueba o rechaza; el editor puede cancelar.
3. Al aprobar, en **una transacción**: se bloquea el proyecto, se verifica que la solicitud siga `pending`, no haya expirado, el proyecto no esté archivado ni pendiente de eliminación, `owner_id` siga siendo `current_owner_at_request` y el solicitante siga siendo editor.
4. Se actualizan `projects.owner_id`, ambos roles y la solicitud.

### Checklist

#### Datos
- [ ] Esquemas de invitaciones, aceptaciones y solicitudes de transferencia con todos los `CHECK` e índices.
- [ ] Índice único parcial `WHERE status = 'pending'` en `ownership_transfer_requests`.

#### Servidor
- [ ] `CreateInvitationService`: genera token aleatorio, guarda solo el hash, rol `editor` o `reader`.
- [ ] `AcceptProjectInvitationService` transaccional (ver bloque anterior).
- [ ] Revocación de invitaciones.
- [ ] Gestión de integrantes: cambiar rol, quitar integrante (sin dejar cero ni más de un propietario).
- [ ] `TransferProjectOwnershipService`: solicitar, aprobar, rechazar, cancelar, expirar.
- [ ] Marcar `expired` de forma perezosa en lecturas.
- [ ] Evitar que el propietario abandone el proyecto sin resolver la propiedad.

#### Frontend
- [ ] Pantalla de integrantes: roles, enlaces de invitación (crear, copiar, revocar).
- [ ] Página de aceptación de invitación con redirección tras autenticarse.
- [ ] Bandeja de solicitudes de transferencia para el propietario.

#### Pruebas
- [ ] Un enlace de un solo uso consumido por dos solicitudes simultáneas: solo una tiene éxito.
- [ ] Repetir una solicitud ya procesada no crea otra membresía ni aceptación.
- [ ] Enlaces revocados, agotados o expirados no se pueden aceptar.
- [ ] Antes de aceptar, la persona no ve datos ni aparece como integrante.

- [ ] Aprobar una transferencia actualiza proyecto, membresías y solicitud de forma atómica.
- [ ] Rechazar o cancelar no cambia la propiedad.
- [ ] Solo existe una solicitud `pending` por proyecto.
- [ ] Una transacción fallida se revierte completa.

### Definición de terminada
- Un equipo de 3 personas (propietario, editor, lector) colabora con permisos correctos.

## Fase 6 — Archivado y eliminación con recuperación
*Meta: ciclo de vida completo del proyecto, con eliminación segura y recuperable.*
*Depende de: Fase 5 · Esfuerzo: 2 sesiones*

### Qué hay de nuevo
- Archivado de proyectos (solo el propietario restaura; los editores pueden solicitar la restauración).
- Solicitud de eliminación con confirmación por nombre y recuperación de 30 días.
- Purga física controlada.
- Eliminación de cuenta con anonimización de autoría.

### Flujo

```text
Proyecto activo o archivado → Solicitud explícita → 30 días de recuperación → Purga física
```

### Checklist

#### Servidor
- [ ] Archivar / restaurar proyecto (`status = archived`), separado del ciclo de eliminación.
- [ ] `RequestProjectDeletionService`: confirmar escribiendo el nombre; fijar `deletion_requested_at` y `purge_after = +30 días`; revocar invitaciones activas; bloquear el uso normal.
- [ ] Cancelar eliminación (limpia los campos y restaura el estado previo).
- [ ] `PurgeProjectService`: transaccional o reintentable e idempotente; verifica `purge_after` antes de borrar.
- [ ] Script de purga ejecutable a mano (por ejemplo `pnpm purge`) que invoque al servicio; la programación automática se define en la Fase 8.
- [ ] Eliminación de cuenta: exige transferir o eliminar proyectos propios; período de recuperación de 30 días; luego borrar credenciales y datos personales, quitar membresías y anonimizar autoría como `Usuario eliminado` (`ON DELETE SET NULL`).
- [ ] Política de copias de seguridad: retención máxima de 30 días y respeto de purgas ya completadas.

#### Frontend
- [ ] Configuración del proyecto: archivar, restaurar, solicitar y cancelar eliminación.
- [ ] Pantalla de proyecto pendiente de eliminación con cuenta atrás.
- [ ] Configuración de cuenta: eliminación con advertencias.

#### Pruebas
- [ ] Solo el propietario puede solicitar la eliminación y requiere confirmación.
- [ ] Un proyecto pendiente no permite operaciones normales ni transferencias.
- [ ] La cancelación restaura el estado funcional anterior.
- [ ] La purga no ocurre antes de `purge_after`.
- [ ] La purga elimina todos los dependientes; no quedan huérfanos.
- [ ] Una purga repetida es segura (idempotente).
- [ ] Un proyecto archivado puede entrar en eliminación.
- [ ] Una restauración desde copia de seguridad no reintroduce proyectos ya purgados.

### Definición de terminada
- Se completa un ciclo real: solicitar → esperar (simulado) → purgar, sin dejar datos.

## Fase 8 — Despliegue
*Meta: publicar por primera vez el MVP terminado para que equipos reales puedan usarlo.*
*Depende de: Fase 7 · Esfuerzo: 1-2 sesiones*

### Qué hay de nuevo
- La aplicación queda publicada en Vercel con una base de datos Supabase de producción.
- Correos reales de verificación y recuperación de contraseña.
- Purga programada de proyectos.

### Checklist

#### Preparación
- [ ] Congelar versiones y lockfile; `pnpm build` sin errores en local.
- [ ] Crear un proyecto Supabase de **producción**, separado del de desarrollo, y aplicar las migraciones.
- [ ] Decidir el tipo de conexión de la app: pooler en modo transacción (recomendado en Vercel serverless) o conexión directa.
- [ ] Revisar RLS en las tablas del esquema público expuesto.

#### Configuración

```text
DATABASE_URL=postgresql://...:6543/postgres   # la app (pooler transaccional)
DIRECT_URL=postgresql://...:5432/postgres     # migraciones (conexión directa)
BETTER_AUTH_SECRET=...                        # secreto de sesiones
BETTER_AUTH_URL=https://tu-dominio            # URL pública base
```

```ts
const client = postgres(process.env.DATABASE_URL!, { prepare: false });
export const db = drizzle(client);
```

**Qué hace cada bloque:**
- Las variables separan dos conexiones: `DATABASE_URL` es la que usa la app en tiempo de ejecución y `DIRECT_URL` la usa Drizzle Kit para migrar.
- `BETTER_AUTH_SECRET` firma las sesiones y `BETTER_AUTH_URL` le indica a Better Auth cuál es la URL pública (necesaria para los enlaces de correo).
- `prepare: false` desactiva las *prepared statements*, que no funcionan con el pooler en modo transacción.
- Las transacciones (`db.transaction`) y `SELECT ... FOR UPDATE` siguen funcionando igual dentro de ese modo.

#### Vercel
- [ ] Conectar el repo a Vercel y cargar las variables de entorno de producción.
- [ ] Configurar dominio y URL base de Better Auth.
- [ ] Configurar un proveedor de correo real para verificación y recuperación.
- [ ] Programar la purga con Vercel Cron. Esto exige un Route Handler protegido por secreto: es la **excepción explícita** a la regla de que el único Route Handler sea el de Better Auth; documentarla.

#### Operación
- [ ] Configurar copias de seguridad con retención máxima de 30 días.
- [ ] Prueba de humo E2E contra producción (registro → proyecto → relación → aprobación).
- [ ] Verificar que ninguna credencial llega al navegador en el build desplegado.

### Definición de terminada
- El MVP está publicado y el recorrido completo funciona en producción.
- Los correos llegan y la purga programada se ejecuta sin errores.

## 7. Deliberadamente fuera del MVP

- Gestión de cursos, docentes y grupos.
- Inteligencia artificial.
- Archivos adjuntos y almacenamiento propio.
- Editores visuales de diagramas.
- Integraciones sincronizadas y enlaces externos (Figma, Drive, GitHub).
- Enlaces públicos de solo lectura y acceso anónimo (un docente entra como lector por invitación autenticada).
- Invitaciones individualizadas por correo.
- Historial completo de versiones y restauración.
- Notificaciones avanzadas, menciones y chat.
- Analítica avanzada.
- Metodologías, tipos de relación y estados de tarea configurables.
- Plantillas creadas o publicadas por usuarios.
- Microservicios, Redis, base de datos de grafos y API pública.

> Si el calendario se reduce, se aplazan primero: comentarios, interfaz de historial y otras funciones complementarias. Se protegen: creación, relación, consulta y validación.

## 8. Riesgos y cómo los cubre este plan

| Riesgo | Mitigación en el roadmap |
|---|---|
| **Adopción:** mantener relaciones a mano es costoso | Meta de ≤ 4 acciones y ≤ 60 s (Fase 3); medición en Fase 9 |
| **Alcance:** auth, invitaciones, permisos y matriz inflan el MVP | Fases deployables; colaboración (Fase 5) después del uso individual (Fase 4); opcionales marcados |
| **Interpretación:** cobertura ≠ calidad | Métricas separadas en UI y documentación (Fases 4 y 7) |
| **Aprobación artificial:** proyecto vacío aprobado | Contenido mínimo independiente de la cobertura; prueba explícita (Fase 4) |
| **Integridad de datos** | Restricciones en PostgreSQL + pruebas de integridad antes de construir pantallas |
